# 1.3 Adaptable Structure

Criteria covered: 1.3.1 through 1.3.6. Use this reference for semantic structure, headings, tables, lists, groups, labels, DOM order, orientation, sensory-independent instructions, autocomplete, and identifying UI purpose.

## Core Requirement

Content must preserve meaning when presented in different ways: screen reader output, browser zoom, small screens, custom styles, speech input, high contrast, translation, and assistive technologies. Visual structure alone is not enough.

## 1.3.1 Info and Relationships

Make information, structure, and relationships programmatically determinable or available in text.

Design and frontend obligations:

- Use headings for real section structure, not for visual size.
- Use lists for grouped list items.
- Use table markup for data tables, with headers and header relationships.
- Use fieldsets or equivalent grouping for related inputs where group context is needed.
- Associate labels, descriptions, errors, and help with the relevant controls.
- Use landmarks and regions to identify major page areas.
- Preserve relationships in cards, dashboards, timelines, filters, tabs, accordions, and comparison layouts.

Do not simulate headings, lists, buttons, links, or tables with visual styling alone.

## 1.3.2 Meaningful Sequence

When sequence affects meaning, the programmatic order must preserve that meaning. CSS layout, responsive reordering, sticky regions, and visual masonry must not create a different reading or focus order.

Check:

- DOM order follows the intended reading and task order.
- Focus order and reading order do not contradict visual order.
- Responsive layouts do not move instructions after the controls they explain.
- Inserted content appears at a logical point in the DOM.
- Tables, multi-column content, timelines, and comparison grids remain understandable linearly.

## 1.3.3 Sensory Characteristics

Instructions must not rely only on shape, color, size, visual location, orientation, or sound.

Use text or programmatic identifiers in addition to sensory cues. Examples:

- "Select Continue" instead of "select the green button".
- "Required fields are marked Required" instead of "required fields are red".
- "Open Account settings" instead of "use the icon on the right".
- "A confirmation message appears" instead of relying only on a sound.

Sensory cues can remain as reinforcement, but they cannot be the only way to understand or operate.

## 1.3.4 Orientation

Content and operation must work in portrait and landscape unless a specific orientation is essential. Essential means the orientation is required for the activity itself, not merely preferred by design.

Design and test:

- Do not lock orientation for web pages or web apps.
- Avoid layouts that hide controls or trap modals after rotation.
- Test virtual keyboard display in both orientations.
- Test media, maps, forms, and dialogs after orientation change.

## 1.3.5 Identify Input Purpose

For fields collecting information about the user, expose the input purpose using appropriate autocomplete tokens where supported.

Apply to common personal-data fields: name, email, telephone, address, username, current password, new password, one-time code, organization, job title, birthday, payment, and shipping details.

Do not use autocomplete values that misrepresent the expected data. A visible label and an autocomplete token are different obligations: the label explains the field to users; the token helps user agents personalize, autofill, and support input.

## 1.3.6 Identify Purpose

At AAA, the purpose of UI components, icons, and regions must be programmatically determinable where markup technologies support it. This supports personalization, symbol sets, simplified interfaces, and assistive adaptation.

Design and frontend obligations:

- Use consistent landmarks and region labels.
- Use clear component names and roles.
- Avoid ambiguous icon-only controls.
- Keep repeated functions identified consistently.
- Use available semantics before custom metadata.

## Tables and Data Relationships

Use data tables only for relational data. Provide:

- a clear caption or nearby title;
- column and row headers where needed;
- scope or equivalent header associations;
- units and sorting state in text or programmatic state;
- no reliance on spatial location alone.

For complex tables, consider simplifying, splitting, or adding summaries. Do not use layout tables for page structure.

## Forms and Groups

Every input needs a label or an accessible name. Related controls need group context when labels repeat or depend on a shared question.

Examples needing group context: radio groups, checkbox groups, segmented controls, date parts, shipping/billing address groups, repeated form sections, and table-based inputs.

Instructions, format requirements, and error messages must be programmatically connected when users need them to complete the field.

## Acceptance Tests

- Inspect headings, lists, landmarks, tables, form labels, groups, and descriptions in the accessibility tree.
- Read the page linearly and confirm meaning is preserved.
- Navigate with keyboard and confirm sequence matches the task.
- Rotate viewport and test portrait and landscape operation.
- Verify autocomplete tokens for user-information inputs.
- Review instructions for sensory-only wording.
- Check UI component and region purpose for AAA targets.

## Common Failures

- Visual headings implemented as styled paragraphs.
- Cards or tiles that read in a different order than the visible workflow.
- Labels implied only by placeholder text or layout.
- Data tables without header relationships.
- Required fields identified only by color.
- Orientation lock for nonessential layouts.
- Autocomplete omitted or wrong on personal-data fields.
- Icon regions and repeated controls with ambiguous purpose.
