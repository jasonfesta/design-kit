# 4.1 Compatible, ARIA, and Status Messages

Covered criteria: 4.1.2 Name Role Value (A) and 4.1.3 Status Messages (AA). SC 4.1.1 Parsing is obsolete and removed in WCAG 2.2; valid code remains a quality practice because it reduces compatibility risk.

Use this for frontend implementation reviews, custom controls, ARIA, web components, live regions, dynamic updates, SPAs, dialogs, menus, tabs, accordions, form errors, async search, and status feedback.

## Native First

Prefer native HTML controls because browsers already expose name, role, value, state, and keyboard behavior when used correctly.

Use ARIA only when:

- Native semantics cannot express the needed role or relationship.
- A custom control is truly necessary.
- Dynamic state must be exposed to assistive technology.
- A live update must be announced without moving focus.

ARIA does not add behavior. Keyboard interaction, focus management, and visual states must still be implemented.

## Name, Role, Value

For every UI component, define:

- Name: what users call it or what action it performs.
- Role: what kind of control it is.
- Value: current value where applicable.
- State: expanded, pressed, selected, checked, current, invalid, disabled, busy, hidden, modal, or similar.
- Properties: relationships such as controls, labelled by, described by, owns, level, set size, position.
- Change notification: updates to user-settable states and values are exposed to user agents and assistive technologies.

If users can change it visually, assistive technologies must be able to perceive and operate that change.

## Accessible Names

Name sources must be intentional.

- Prefer visible text labels.
- Use programmatic labels for icon-only controls.
- Use descriptions for supplemental hints, not as the primary name.
- Do not create duplicate or contradictory names.
- Do not override useful visible labels with less useful `aria-label` values.
- Ensure visible label text appears in the accessible name for speech input compatibility.

## Custom Control Specification

Before implementation, document:

- Native equivalent, if any.
- Required role.
- Accessible name source.
- Required states and properties.
- Keyboard model.
- Focus entry, internal movement, and focus return.
- Pointer/touch behavior.
- Visual state mapping.
- Status announcements.
- Disabled and read-only behavior.
- Error behavior.

If this cannot be specified clearly, use a simpler native pattern.

## Live Regions and Status Messages

A status message gives users information about a change without receiving focus. At AA, status messages must be programmatically determinable so assistive technologies can present them.

Use status messaging for:

- Search results count changed.
- Item added or removed.
- Save succeeded.
- Form submission failed while focus remains in place.
- Loading started or completed when relevant.
- Filter applied.
- Cart updated.

Do not move focus to routine status messages. Move focus only when the user must take action or when a new context opens.

## Polite vs Assertive

| Urgency | Announcement approach |
|---|---|
| Routine success, count, loading, saved state | Polite status. |
| Error that blocks current task but focus stays in context | Assertive or focused error summary, depending on severity. |
| Emergency or destructive failure | Assertive plus visible message; focus may move if action is required. |
| Repeated progress updates | Throttle or summarize; do not spam announcements. |

Avoid using live regions for content that updates constantly, such as timers or market data, unless the user explicitly requests announcements.

## Hidden, Inert, and Disabled Content

- Hidden content must not remain in the focus order.
- Inactive background under modal UI should not be operable by keyboard or assistive technology.
- Disabled controls should expose disabled state and not trap focus.
- Content visually hidden for assistive technology must still be meaningful when announced.
- Content hidden from assistive technology must not be the only source of meaning.

## ARIA Risk Rules

- Do not change a native element role unless necessary.
- Do not use `role="button"` on non-buttons when a real button works.
- Do not use menu roles for ordinary site navigation unless implementing an application-style menu keyboard model.
- Do not use `aria-hidden="true"` on focusable content or ancestors of focusable content.
- Do not use `aria-live` on large containers that change frequently.
- Do not mark something selected, expanded, or pressed unless the visual state matches.
- Do not create relationships to missing IDs.

## Acceptance Tests

- Inspect accessibility tree for name, role, value, state, and relationships.
- Operate custom controls with keyboard and screen reader.
- Verify state changes are announced or exposed.
- Trigger async updates and confirm useful status messages.
- Check hidden and modal states for focus leakage.
- Test with at least one browser/screen reader combination relevant to the audience.
- Confirm no ARIA conflicts with native semantics.

## Common Failures

- Icon button has no accessible name.
- Custom checkbox exposes no checked state.
- Accordion visually expands but `aria-expanded` remains false.
- Toast appears visually but is not announced.
- Live region announces entire page repeatedly.
- Focusable content inside `aria-hidden` container.
- Dialog opens without modal semantics or focus management.
- Site navigation uses application menu roles and breaks expected keyboard behavior.
