# 2.1 Keyboard Accessible

Criteria covered: 2.1.1 Keyboard (A), 2.1.2 No Keyboard Trap (A), 2.1.3 Keyboard No Exception (AAA), and 2.1.4 Character Key Shortcuts (A). Use this reference for interactive UI, custom widgets, modals, menus, drawers, embedded content, and SPA states.

## Core Requirement

Every function must be operable from a keyboard interface. This benefits keyboard users, switch users, screen reader users, voice-control users, and many assistive technologies that emulate keyboard behavior.

Pointer support is not a substitute for keyboard support. Keyboard support is not only tabbing; it includes activation, selection, movement, dismissal, editing, and recovery.

## 2.1.1 Keyboard

All functionality must work without requiring a mouse, touch gesture, stylus, drag, hover, or device motion. The only A-level exception is functionality where the path of movement is essential to the result, such as freehand drawing.

Design obligations:

- Specify keyboard operation before implementation.
- Provide keyboard alternatives for drag, reorder, resize, swipe, pinch, and hover actions.
- Make hidden controls available when focus reaches the relevant area, not only on pointer hover.
- Avoid controls that visually appear interactive but are not keyboard reachable.

Frontend obligations:

- Use native controls where possible.
- Ensure custom controls expose role, name, state, value, and keyboard behavior.
- Do not remove focusability from interactive elements.
- Do not use positive tabindex to force arbitrary focus order.

## 2.1.2 No Keyboard Trap

If keyboard focus can enter a component, it must be possible to leave it with standard keys or clearly documented keys.

High-risk areas:

- modals and drawers;
- embedded maps, videos, iframes, code editors, and third-party widgets;
- menus and comboboxes;
- carousels;
- custom grids and spreadsheets;
- cookie banners and chat widgets.

For modal dialogs, focus may be contained while the dialog is open, but users must have an operable close/cancel path and focus must return logically after close.

## 2.1.3 Keyboard No Exception

At AAA, every function must be available from keyboard with no path-dependent exception. If the product includes drawing, spatial manipulation, annotation, map editing, or gesture-based creative tools, provide a keyboard method that achieves the same functional outcome.

## 2.1.4 Character Key Shortcuts

If a shortcut uses only letters, numbers, punctuation, or symbols, at least one must be true:

- users can turn it off;
- users can remap it to include a modifier or non-printable key;
- the shortcut works only when the relevant component has focus.

This prevents conflicts with speech input, screen readers, browser shortcuts, and user typing.

## Keyboard Behavior Specification

For each interactive pattern, define:

- how focus enters and exits;
- which element receives initial focus;
- Tab and Shift+Tab behavior;
- Enter and Space behavior;
- Escape behavior for dismissible UI;
- arrow-key behavior where the pattern requires it;
- Home/End behavior for ordered composite widgets where useful;
- what happens after deletion, insertion, filtering, sorting, saving, canceling, or route changes.

Do not invent keyboard models when a standard native element or established pattern exists.

## Roving Focus and Composite Widgets

Composite widgets may keep one Tab stop for the group and use arrow keys inside the group. This can be appropriate for tabs, menus, toolbars, radio-like groups, grids, and listboxes.

Use roving focus only when the component behaves as a composite widget. Do not use it to hide a large number of normal links or buttons from the Tab sequence.

The focused item, selected item, and active item must be visually and programmatically clear.

## Focus Return Rules

When a temporary UI closes, return focus to the control that opened it unless that control no longer exists or another destination is more logical.

After destructive actions, insertion, deletion, filtering, or pagination, place focus where the user can continue without losing context.

After route changes in SPAs, move focus to a logical page-level target and update the document title.

## Acceptance Tests

- Start at the browser address bar and complete every task with keyboard only.
- Verify every actionable element receives focus or has an accessible keyboard path.
- Confirm no focus trap exists in modals, embeds, menus, drawers, and widgets.
- Test activation with Enter and Space where appropriate.
- Test Escape for dismissible overlays.
- Test shortcut settings or focus scoping for single-character shortcuts.
- Verify focus return after close, cancel, submit, save, delete, and navigation.
- Repeat at mobile and desktop breakpoints and at high zoom.

## Common Failures

- Click handlers on non-focusable elements.
- Controls revealed only on mouse hover.
- Modal traps focus with no keyboard close path.
- Custom dropdown opens with keyboard but cannot select or close.
- Drag-and-drop is the only way to reorder.
- Positive tabindex creates confusing focus order.
- Single-letter shortcuts trigger while users dictate or type.
- Focus disappears after a route change or item deletion.
