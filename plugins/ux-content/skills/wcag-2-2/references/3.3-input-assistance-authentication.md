# 3.3 Input Assistance and Authentication

Covered criteria: 3.3.1 through 3.3.9.

Use this for forms, checkout, onboarding, profile editing, admin tools, search filters, login, MFA, CAPTCHA, password reset, settings, destructive actions, and any flow that collects or confirms user input.

## Labels and Instructions

Every required input needs a label or instruction that tells users what to provide.

- Keep labels visible and persistent.
- Programmatically associate labels with controls.
- Put format requirements before the user submits.
- Identify required fields in text, not only color or symbol.
- Group related choices with a group label.
- Explain unusual consequences before the input.

Placeholders can provide examples, but they are not a substitute for labels.

## Error Identification

When an input error is automatically detected:

- Identify the item in error.
- Describe the error in text.
- Associate the error message with the field.
- Preserve the user's entered data unless it is unsafe to do so.
- Provide an error summary for long or multi-error forms.
- Move focus to a logical place after submission errors, usually the summary or first invalid field.

## Error Suggestions

At AA, provide correction suggestions when known unless suggestions would compromise security or the purpose of the content.

Good suggestions:

- "Use the format name@example.com."
- "Password must be at least 12 characters."
- "Choose a date after today."
- "This username is taken. Try one of these available usernames."

Avoid exposing sensitive details, such as confirming which part of a login credential is valid.

## Error Prevention

For legal, financial, data-modifying, data-deleting, or test-submission actions at AA, at least one must be true:

- Reversible: user can undo or cancel after submission.
- Checked: data is checked and user can correct errors.
- Confirmed: user can review, confirm, and correct before final submission.

At AAA, apply the same protection to all information submissions.

Use explicit confirmation for irreversible or high-impact actions. Avoid vague buttons such as "OK" for destructive actions.

## Help

At AAA, context-sensitive help is available. Even below AAA, complex forms should provide help near the point of need.

Help can include:

- Field-level hints.
- Examples.
- Eligibility explanations.
- Link to policy or calculation details.
- Contact/help mechanism.
- Step-by-step guidance.

Help must be accessible by keyboard and assistive technology and must not cover the field it explains.

## Redundant Entry

Within the same process, information previously entered by or provided to the user and required again must be auto-populated or available for selection unless:

- Re-entry is essential.
- Re-entry is required for security.
- Previously entered information is no longer valid.

Examples:

- Billing address can be copied to shipping address.
- Previously entered email should not be requested again on the next step.
- Account details already known should be selectable.
- Confirmation pages show entered information for review rather than asking for retyping.

## Accessible Authentication

Authentication must not require cognitive function tests unless allowed alternatives or assistance are provided.

Cognitive function tests include memorizing a password, transcribing characters, solving a puzzle, calculating, recognizing patterns, or remembering personal facts.

At AA, a cognitive function test is allowed only when at least one is provided:

- Another authentication method that does not rely on a cognitive function test.
- A mechanism to assist completion, such as password managers or copy/paste.
- Object recognition.
- Recognition of non-text content the user provided to the website.

At AAA, only the alternative or assistance mechanisms qualify; object recognition and personal-content recognition are not sufficient exceptions.

## Authentication Design Rules

- Support password managers.
- Allow paste into username, password, one-time code, and recovery fields unless a documented security requirement prevents it.
- Do not require users to memorize or transcribe unnecessary information.
- Provide accessible MFA options.
- Avoid CAPTCHA where possible; if used, provide accessible alternatives.
- Keep error messages clear but not security-leaking.
- Preserve progress after login or re-authentication.

## Form State Matrix

For each form, define:

- Empty state.
- Valid entry state.
- Invalid entry state.
- Required missing state.
- Disabled/read-only state.
- Loading/submitting state.
- Submission success.
- Submission failure.
- Session expiry and recovery.
- Review/confirmation/undo state for high-impact actions.

## Acceptance Tests

- Submit empty and invalid forms; verify text errors, associations, and focus behavior.
- Use screen reader form navigation to identify labels, required state, hints, and errors.
- Complete the process without retyping previously provided information unless an exception is documented.
- Complete login with password manager and pasted credentials/codes.
- Test destructive, financial, legal, and data-changing flows for review, confirm, undo, or error checking.
- Verify help is discoverable, accessible, and does not obscure fields.

## Common Failures

- Error shown only by red border.
- Error summary links do not move focus to fields.
- Required fields identified only by an asterisk with no explanation.
- Password field blocks paste or password managers.
- MFA requires transcription from an image.
- Confirmation page repeats data entry instead of allowing review.
- User must enter the same address multiple times.
- Destructive action has no review, undo, or meaningful confirmation.
