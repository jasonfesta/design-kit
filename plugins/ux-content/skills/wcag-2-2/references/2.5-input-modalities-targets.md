# 2.5 Input Modalities and Targets

Criteria covered: 2.5.1 through 2.5.8. Use this reference for touch, pointer, speech input, gestures, drag/drop, maps, sliders, cards, icon buttons, mobile layouts, and target sizing.

## Core Requirement

Users must not be forced into one physical input method. Designs must work with keyboard, pointer, touch, stylus, speech input, switch control, and assistive technologies where applicable.

## 2.5.1 Pointer Gestures

Multipoint gestures or path-based gestures need a single-pointer alternative unless the complex gesture is essential.

High-risk gestures:

- pinch to zoom;
- two-finger rotate;
- swipe to reveal actions;
- drawing a shape to activate;
- lasso select;
- map pan/zoom as the only way to choose a location;
- drag along a precise path.

Provide buttons, fields, list alternatives, step controls, or direct actions that accomplish the same result.

## 2.5.2 Pointer Cancellation

Pointer actions should not fire only on the down-event unless essential. Users must be able to cancel or reverse accidental activation.

Safer behavior:

- activate on release, not press;
- allow users to move away before release to cancel;
- provide undo for destructive actions;
- avoid immediate irreversible actions on tap-down;
- keep press-and-hold alternatives accessible.

## 2.5.3 Label in Name

When a control has visible text, the accessible name must contain that visible text. This is critical for speech input users who say the label they see.

Examples:

- Visible "Save changes" should not have accessible name "Submit".
- Visible "Search" icon button should not be named "Magnifier".
- Visible card action text should be part of the interactive element's accessible name.

The visible label does not need to be the only accessible name, but it must be included in a sensible order.

## 2.5.4 Motion Actuation

Functionality triggered by device motion or user motion must also be available through a non-motion interface, and motion actuation can be disabled unless essential.

Examples needing alternatives: shake to undo, tilt to scroll, rotate device to reveal controls, camera gesture to submit, or movement-based game controls.

## Target Size

| Criterion | Level | Requirement summary |
|---|---:|---|
| 2.5.8 Target Size Minimum | AA | Targets are at least 24 by 24 CSS px, or meet spacing/equivalent/inline/essential/user-agent exceptions. |
| 2.5.5 Target Size Enhanced | AAA | Targets are at least 44 by 44 CSS px, with narrower exceptions. |

Design larger than the minimum where touch is common. Dense enterprise screens still need adequate target area, spacing, and keyboard alternatives.

Target size is the actionable hit area, not only the visible icon. A 16 px icon can pass if its button target is large enough and visually understandable.

## 2.5.6 Concurrent Input Mechanisms

Do not restrict the user to one input mechanism unless restriction is essential, needed for security, or required to respect user settings.

Do not disable touch because a mouse is detected. Do not disable keyboard because touch is primary. Do not require hover when the device also supports touch.

## 2.5.7 Dragging Movements

At AA, functionality that uses dragging must have an alternative that does not require dragging, unless dragging is essential.

Provide alternatives for:

- reordering list items;
- moving cards across columns;
- resizing panels;
- selecting ranges;
- setting slider values;
- positioning objects on a canvas;
- uploading by drag-and-drop.

Alternatives may include move up/down buttons, numeric fields, menus, select controls, stepper controls, checkboxes, or browse buttons. The alternative must be available, not hidden behind documentation.

## Speech Input Considerations

Speech input users rely on visible labels and stable target names. Avoid controls whose visible label differs from the accessible name. Avoid unlabeled icon-only controls. Ensure dynamic labels and states remain concise and pronounceable.

## Mobile and Touch Considerations

- Keep target spacing adequate to prevent accidental activation.
- Avoid placing destructive actions next to common actions without confirmation or undo.
- Ensure touch controls are not hidden under sticky overlays.
- Test with zoom and text resizing; enlarged text should not shrink targets or cause overlap.
- Provide non-hover ways to access actions revealed on desktop hover.

## Acceptance Tests

- Complete gesture-based tasks with a single pointer and with keyboard where relevant.
- Test pointer cancellation by pressing, moving away, and releasing.
- Inspect accessible names against visible labels.
- Turn off or avoid motion actuation and complete the same function.
- Measure target sizes and spacing at each breakpoint.
- Switch between keyboard, mouse, touch, stylus, and speech input where available.
- Complete drag-and-drop functions without dragging.

## Common Failures

- Swipe is the only way to delete or reveal row actions.
- Dragging is the only way to reorder a list.
- Button activates on mouse down and cannot be canceled.
- Accessible name omits the visible button text.
- 16 px icon button has no larger hit area.
- App disables keyboard focus on mobile.
- Shake-to-submit has no button alternative.
- Hover-only card controls disappear on touch devices.
