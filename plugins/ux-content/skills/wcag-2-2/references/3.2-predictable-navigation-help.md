# 3.2 Predictable Navigation and Help

Covered criteria: 3.2.1 On Focus (A), 3.2.2 On Input (A), 3.2.3 Consistent Navigation (AA), 3.2.4 Consistent Identification (AA), 3.2.5 Change on Request (AAA), and 3.2.6 Consistent Help (A).

Use this for navigation, account areas, settings, help mechanisms, repeated flows, filters, form controls, route changes, popups, support entry points, and dynamic UI.

## Context Changes

A change of context includes a major change in content, viewport, focus, route, window, or meaning that can disorient users.

Examples:

- Submitting a form.
- Opening a new window.
- Moving focus to a different component.
- Navigating to a new route.
- Replacing the main content.
- Launching a modal.
- Reordering page content in a way that changes the task.

## On Focus

Receiving focus must not initiate a context change.

Avoid:

- Opening dialogs as soon as a field receives focus.
- Submitting or navigating when a link or control receives focus.
- Moving focus elsewhere automatically on focus.
- Expanding content in a way that changes focus order unpredictably.

Revealing non-disruptive help text on focus can be acceptable when it does not change context and meets hover/focus content requirements.

## On Input

Changing a control setting must not cause an unexpected context change unless users are advised before using the control.

Risky controls:

- Select menu that navigates immediately.
- Toggle that submits settings instantly without notice.
- Radio group that changes route or replaces content on selection.
- Filter that moves focus or resets the page without notice.
- Date picker that closes and moves focus unpredictably.

Prefer explicit action buttons such as Apply, Save, Continue, Search, or Update results.

## Consistent Navigation

Repeated navigation mechanisms must occur in the same relative order across pages in a set unless the user initiates a change.

Applies to:

- Header links.
- Sidebar navigation.
- Footer links.
- Breadcrumb placement.
- Account menu.
- Product switcher.
- Help/support entry point when part of repeated navigation.

Responsive layouts may change visual presentation, but the relative order and purpose should remain predictable.

## Consistent Identification

Components with the same functionality must be identified consistently.

- Use the same label for the same action.
- Use the same icon for the same meaning.
- Use the same accessible name for repeated icon-only controls.
- Do not use one label for different actions.
- Do not switch between "Close", "Dismiss", "Cancel", and "Back" unless they mean different things.

Consistency includes visible text, accessible names, descriptions, and state language.

## Change on Request

At AAA, context changes happen only when the user requests them, or a mechanism exists to turn them off.

Design for explicit consent:

- Do not auto-open new windows.
- Do not auto-refresh main content when the user is reading.
- Do not redirect after a delay unless necessary and clearly controlled.
- Do not automatically move to the next step after field completion unless users requested that behavior.

## Consistent Help

If help mechanisms are repeated on multiple pages, they must occur in the same relative order. Covered help mechanisms include:

- Human contact details.
- Human contact mechanisms such as chat, email form, phone link, or appointment request.
- Self-help options such as FAQ, documentation, knowledge base, or help center.
- Fully automated contact mechanisms such as chatbots.

The mechanism may be directly on the page or linked from the page. Keep it predictable in placement and order.

## Help Behavior

Help should not create new barriers.

- Help controls are keyboard-operable.
- Chat widgets do not obscure focused controls.
- Automated help discloses that it is automated.
- Support links have clear names.
- Help content uses plain language and does not rely only on screenshots.
- Opening help does not discard user work.

## Acceptance Tests

- Tab through controls and verify focus alone does not navigate, submit, or open disruptive UI.
- Change each input and verify context changes are expected or announced before use.
- Compare repeated navigation order across pages, roles, and breakpoints.
- Compare labels and icons for the same functions across the product.
- Locate help on multiple pages and verify it appears in the same relative order.
- Test chat/help widgets at zoom and with keyboard focus.

## Common Failures

- Select menu navigates immediately without warning.
- Focus on a field opens a modal that traps users.
- Same trash icon means "remove from list" in one place and "delete permanently" elsewhere.
- Help button moves from header to footer unpredictably across pages.
- Chat bubble covers the submit button or keyboard focus.
- Filter controls auto-update results and reset focus without warning.
- New window opens from an input change rather than explicit request.
